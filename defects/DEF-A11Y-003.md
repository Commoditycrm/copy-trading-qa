# DEF-A11Y-003 — Link-in-text, prohibited ARIA, and non-focusable scroll region (serious WCAG A/AA)

- **Severity:** Medium (a11y **serious**) · **Priority:** P2 · **Status:** Confirmed (reproduced ×2, both a11y-suite runs) · **Date:** 2026-08-04
- **Confirming tests:** `A11Y-SCAN` (page-scans.spec.ts) · **Environment:** local-qa full stack, Chromium

## Summary
Three distinct serious axe violations across pages:

| axe rule | WCAG | Page(s) | Count | Meaning |
|---|---|---|---|---|
| `link-in-text-block` | 1.4.1 Use of Colour (A) | `/terms` (1), `/privacy` (2) | 3 | In-paragraph links are distinguished from surrounding text by **colour alone** (no underline/other cue). |
| `aria-prohibited-attr` | 4.1.2 (A) | `/calendar` (1) | 1 | An ARIA attribute is applied to an element/role that does not support it (ignored/mis-announced by AT). |
| `scrollable-region-focusable` | 2.1.1 Keyboard (A) | `/performance` (2) | 2 | A scrollable region is not keyboard-focusable — its content can't be scrolled without a mouse. |

## Reproduction
Load each page and run axe-core (WCAG A+AA); observe the rules above. Deterministic; reproduced on both
a11y-suite runs. Offending nodes attached per test as `axe-*` evidence.

## Impact
- **link-in-text-block:** colour-blind users can't tell links from text on the legal pages.
- **aria-prohibited-attr:** screen readers mis-/under-announce the calendar element.
- **scrollable-region-focusable:** keyboard-only users can't scroll the `/performance` region.

## Suggested fix (app team)
Underline (or otherwise non-colour cue) in-text links; remove the unsupported ARIA attribute on
`/calendar`; add `tabindex="0"` (and a label) to the `/performance` scroll container. Remove each rule from
the page `KNOWN` baseline as it's fixed.
